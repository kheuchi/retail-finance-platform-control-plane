# Story 6.3 · Semantic releases

Planned · Epic 6 · 2026-10-28 · Data repo · 🟡 In review ([data PR #47](https://github.com/kheuchi/retail-finance-data-products/pull/47))

## TL;DR

| | |
|---|---|
| Goal | Every change that reaches `main` has a version number, a tag and release notes |
| Why | No tags or releases existed: nothing to roll back to, nothing to cite in a change record |
| How | python-semantic-release reads the conventional-commit titles (`feat:` minor, `fix:` patch, `!` major) and tags `main` |
| First version | `v1.0.0`: what runs today |
| Not done | The deploy workflow doesn't deploy by tag yet |

## Context

> **TL;DR:** we already write conventional commits; we never turned them into versions.

| Question | Before |
|---|---|
| Which code is deployed? | "Whatever `main` was at the last deploy run" |
| What changed between two deploys? | Read the git log |
| Roll back | Revert commits by hand |

## Design

> **TL;DR:** tag only; nothing committed back, because `main` is protected.

| Choice | Why |
|---|---|
| python-semantic-release, pinned by SHA | Python repo; reads our existing commit titles |
| Runs on every push to `main` | One merged PR = at most one release |
| No commit back (no version bump in `pyproject.toml`, no CHANGELOG file) | `main` requires a PR and checks, admins included; a bot commit would be rejected. The tag is the version |
| No release PR (release-please style) | PRs opened with `GITHUB_TOKEN` don't trigger the required checks, so they could never merge |
| `contents: write` on the release job only | Workflow default stays read-only |

Later: the deploy workflow takes a tag as input, so a rollback is "deploy `v1.2.0`".

## Acceptance criteria

- [x] Dry run on a clone of the branch as `main` computes `v1.0.0`.
- [ ] PR reviewed and merged; required checks green.
- [ ] The Release workflow creates tag `v1.0.0` and a GitHub release with notes.
- [ ] The next `fix:` merge creates `v1.0.1` without anyone touching it.
