## Context

> **TL;DR:** "drift" means two different things; both are blind spots today.

| Kind | Question | Today |
|---|---|---|
| Model (data) drift | Does this month's data still look like what the model was built on? | Not measured |
| Config drift | Is the deployed job still what Git says? | Push deploy: a manual edit in the UI stays until the next deploy |

## Design

> **TL;DR:** PSI for populations, `bundle plan` for configuration.

**PSI (population stability index):** split the reference months into 10 bins by quantile, count
the share of the current month in each bin, sum `(cur − ref) × ln(cur / ref)`. Rule of thumb:
< 0.1 stable, 0.1-0.2 watch, > 0.2 drift.

| Model | Features checked | Reference |
|---|---|---|
| Cashier refunds | its 5 features | The months 4-12 before the month checked (same gap as the margin baseline) |
| Store margin | its 2 features | Same |
| Forecast | monthly net sales per store | Same |

**Honest limit, stated up front:** PSI measures a shift of the *whole population*. One cashier or
one store out of 40 (the planted frauds) barely moves it; catching those is the detectors' job.
PSI catches a chain-wide change: a new promotion policy, a pipeline bug that halves refunds,
a currency problem.

**Config drift:** `databricks bundle plan -o json` as the deployer, nightly and on demand. Any
create, update or delete on main's configuration fails the workflow (the email comes from GitHub).

## Acceptance criteria

- [ ] PSI per feature for the last 6 complete months of each model, in `ops.model_drift` (model, feature, month, psi, status, gold_run) and as MLflow metrics.
- [ ] Unit tests: same distribution → stable; shifted distribution → drift; constant reference → no crash.
- [ ] Drift never fails the ML job; it prints a summary.
- [ ] The drift workflow passes when the workspace matches main.
- [ ] Proof: a manual change in the workspace (unpausing the schedule, [6.1](6.1-scheduled-pipeline.md)) fails the workflow; a deploy clears it.
