## Context

> **TL;DR:** who owns the tables vs who owns the code: two repos, two pipelines.

The **catalog** is infrastructure (infra repo, Terraform). The **jobs** are data code
(data repo, Databricks Asset Bundle). A bundle is one YAML that packages code, job
definition and target workspace, deployed like an app.

## Bundle, wheel, job

> **TL;DR:** the wheel is the code, the job is the recipe, the bundle ships both together.

Think of shipping a meal kit:

| Term | What it is | Analogy |
|---|---|---|
| **Wheel** (`.whl`) | Python's package format: our code zipped into one installable file, built by `python -m build` | The ingredients, packed in one box |
| **Job** | A Databricks definition of what to run, on which cluster, in which order: tasks, cluster size, policy, timeout, run-as identity | The recipe card: "cook step 1, then step 2, on this stove" |
| **Bundle** | One YAML project (`databricks.yml` + `resources/*.job.yml`) listing the wheel to build, the jobs, and the target workspace | The delivery: box and recipe arrive together, versioned, at the right kitchen |

In our flow:

1. GitHub Actions runs `databricks bundle deploy`.
2. That builds the wheel and uploads it to `finance.ops.artifacts`.
3. It creates or updates the jobs through the Databricks API (push, not pull: nothing
   reverts a manual change until the next deploy).
4. When a job runs, Databricks starts a job cluster, installs the wheel, calls an entry
   point (e.g. `build_silver`), and shuts the cluster down.

Terraform (infra repo) builds the platform the jobs run on; the bundle (data repo) ships
the workloads. "Run as terraform-platform" is just the service principal's name, not
Terraform running the job ([4.5](4.5-split-service-principals.md) splits that identity).

## Tricky parts

> **TL;DR:** where code lives decides who can change what runs as the principal.

### 1. Not `/Workspace/Shared`
- **Risk:** any user can edit files in Shared, and the job runs **as the service principal**.
  Editing the code there = acting with its privileges.
- **Fix:** deploy into the principal's own folder.

### 2. Wheel path is relative to the YAML file
- **Symptom:** deploy could not find the wheel.
- **Cause:** `dist/*.whl` in `resources/ingest.job.yml` resolves from `resources/`, not the repo root.
- **Fix:** `../dist/*.whl`.

### 3. Required checks via the API
- **Symptom:** `gh api` PATCH on required status checks returned 404.
- **Fix:** PUT the full branch protection object again with the new checks.

### 4. No sudo, no internet on clusters
- Databricks CLI v1.18.0 installed as a binary in `~/.local/bin`. The wheel declares **no
  dependencies**: numpy, pandas, pyspark come from Databricks Runtime 17.3 LTS.
