## Context

> **TL;DR:** before this, nothing recorded API calls at all.

For finance this is the core of audit: proving who changed the pipeline behind a
revenue number, and that the record was not altered.

## What we built

> **TL;DR:** S3 is the record, CloudWatch is the trigger.

| Piece | Setting | Why |
|---|---|---|
| CloudTrail | All regions, global events, log file validation, data events on the state bucket | An attacker's favourite trick is acting in an unused region |
| Audit bucket | 365 days, versioned, TLS only | Durable record |
| CloudWatch Logs | 90 days | Only a trigger copy; cheaper |
| Filters | `BreakGlassAdminWrite`, `RootAccountUsed` | Change should come from CI, never a person or root |

## Tricky parts

> **TL;DR:** a silent filter, an email in spam.

### 1. `$.readOnly = false` never matches
- **Symptom:** filter deployed, test write done, alarm stayed green.
- **Cause:** that syntax is valid but compares against a string; the field is a boolean.
- **Fix:** `$.readOnly IS FALSE`. Retested with a real write.
- **Lesson:** a detection is not done until you have seen it fire.

### 2. The alarm nobody would have seen
- **Cause:** the SNS confirmation went to spam, in a different mailbox from the AWS account email.
- **Fix:** confirmed. Now in the control matrix as evidence "tested".

### 3. Side effect worth knowing
- Terraform's state-lock writes count as "admin writes" when run from a workstation, so
  local runs trigger the alarm. That is intended: routine change goes through CI.

## Proof

- Alarm reached ALARM within minutes of a deliberate break-glass write; email received.
- Applied through the pipeline in one run: 10 added, 1 changed (two-phase pattern, [1.3](1.3-least-privilege-deploy-role.md)).
