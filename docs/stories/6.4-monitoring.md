# Story 6.4 · Monitoring of data, models and agent

## TL;DR

| | |
|---|---|
| Question | Is the data fresh and right, are the models still good, is the agent behaving, and who gets told when not? |
| Today | The signals exist in tables (`ops.dq_results`, `ops.model_drift`, `ops.agent_runs`), but nobody is told unless a job fails |
| Missing | One dashboard, alerts on what matters, an owner for each alert |
| Rule | Every signal has a threshold, an owner and a runbook; otherwise it's noise |

## What we have

> **TL;DR:** we record a lot; we alert on almost nothing.

| Layer | Recorded | Alert today |
|---|---|---|
| Pipeline | Job runs, retries | ✅ Email when the scheduled job fails (6.1) |
| Data | Quality checks per run (`ops.dq_results`), Gold certification (`ops.gold_certification`) | ❌ A failed gate stops the run; no message on a "passed but odd" run |
| ML | PSI drift per feature (`ops.model_drift`), metrics in MLflow | ❌ Drift is written, nobody is told |
| Agent | Traces, tokens, cost per run (`ops.agent_runs`), approvals (`ops.agent_approvals`) | ❌ None |
| Infra and cost | CloudTrail, CloudWatch alarms, AWS and Databricks budgets | ✅ Root use, break-glass, budgets |

## What we should have built

> **TL;DR:** four layers, a few signals each, all landing in one place.

| Layer | Signal | Example threshold | Tool |
|---|---|---|---|
| **Data** | Freshness: hours since the last Bronze file | No new file by 07:00 | Databricks Lakehouse Monitoring or a SQL alert |
| | Volume: rows per source vs the same weekday | ±30% | Same |
| | Quality: share of rows set aside in Silver | > 1% | `ops.dq_results` + SQL alert |
| | Reconciliation: GL vs POS gap | Any unexplained gap > EUR 1k | `gold` reconciliation table |
| **ML** | Input drift (PSI) | > 0.2 on any feature | `ops.model_drift` (have it) + alert |
| | Forecast accuracy once actuals arrive | MAPE worse than the baseline 2 months in a row | MLflow + SQL alert |
| | Detector usefulness | Share of flagged cases confirmed by reviewers < 20% | Needs a review outcome table (not built) |
| | Model age | Not retrained in 2 months | MLflow registry |
| **Agent** | Failure rate, latency, cost per run | > 5% failed; > EUR 1 per run | `ops.agent_runs`, Google Cloud Monitoring |
| | Figure-check failures (a number not from a tool) | Any | Agent traces |
| | Approval rate of drafts | < 50% approved without edits | `ops.agent_approvals` |
| | Quality on a fixed test set | Score drops after a prompt or model change | Offline evaluation in CI |
| **Platform** | Job failures, cluster cost, budget | As today | Databricks + AWS budgets (have them) |

## One place to look

> **TL;DR:** one dashboard for the team, one line per layer, green or red.

A Databricks SQL (or Power BI) dashboard reading the `ops` tables:

| Tile | Shows |
|---|---|
| Data | Last load time per source, rows vs normal, quality failures |
| ML | PSI per model, forecast error vs baseline, last training date |
| Agent | Runs, failures, cost, approval rate this month |
| Cost | Spend vs budget, AWS and Databricks |

## Alerts

> **TL;DR:** few alerts, each with an owner and a first step.

| Alert | Goes to | First step |
|---|---|---|
| Data late or wrong | Data engineer on duty | Check the source drop and the Silver quarantine |
| Model drift or accuracy loss | ML owner | Compare with last month; retrain or fall back to the baseline |
| Agent failing or costly | Agent owner | Read the trace; pause the agent if needed |
| Budget | Platform owner | Find the cluster or job, stop it |

Delivery: email first (as today), then the team's chat channel. Every alert links to its runbook.

## Not built, and why

> **TL;DR:** time and cost; the trial ended and the workspace is switched off.

We stopped at recording the signals. With more time, the order would be: SQL alerts on data freshness and
drift (cheap, an hour each), the dashboard, then agent and accuracy alerts. Lakehouse Monitoring would
replace some of the hand-written checks but costs serverless compute.
