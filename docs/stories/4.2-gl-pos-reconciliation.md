## Context

> **TL;DR:** revenue in the books must come from real sales; manual journals are the classic way to fake it.

| Term | Meaning | In our data |
|---|---|---|
| **POS** (point of sale) | The tills: every receipt line, as it happened in the store | `silver.pos_sales`, 3.9m lines |
| **GL** (general ledger) | The accounting books: every amount booked to an account (revenue, cash, VAT...) with debit = credit | `silver.gl_journal`; revenue is account 4000 |
| **Reconciliation** | Proving two independent records agree, and explaining every difference | GL revenue vs POS net sales, per store and day |

Normally each day's POS sales are summarised into one GL journal, so both sides match.
A revenue journal typed in by hand with no sales behind it inflates revenue in the books:
a classic way to fake results. Anomaly A3 ([3.1](3.1-synthetic-accounting-data.md)) plants
four of them in August 2026.

## How it works

> **TL;DR:** compare per store and day; attribute differences by amount, never by label.

**Compare.** POS lines are converted to EUR unrounded and each day is rounded once, exactly as
the daily journal is booked. A probe on the full data before any code showed this gives a match
to the cent on every clean store-day, so the tolerance is EUR 0.01.

**Attribute.** On each store-day with a difference:

| Situation | Verdict |
|---|---|
| No POS sales at all | Every revenue journal: "no matching POS sales" |
| Exactly one journal equals the POS total | It explains the sales; every other journal: "no matching POS sales" |
| Several journals equal the POS total | All of them: "duplicate posting" |
| None equals it | The day, once: "difference not attributable to a journal" |

The journal's `source` field is never read, so a fake calling itself POS is still caught.

**Outputs.** `gold.recon_gl_pos` (store × day), `gold.recon_gl_pos_monthly`, `gold.recon_exceptions`,
and one row per run in `ops.detection_scores` when an answer key exists (synthetic data only).
Exceptions are findings, not job failures.

**Guards.** The job refuses to write if POS or revenue lines are empty, any POS line lacks an FX
rate, or `pos_sales`/`gl_journal` rows sit in Silver quarantine.

## Tricky parts

> **TL;DR:** the logic was simple; not blaming the innocent was not.

### 1. Rounding decides everything
- Summing Silver's 4-decimal EUR line amounts drifts by cents on CHF stores. Converting unrounded
  and rounding once per day reproduces the ledger exactly: 21,218 days at EUR 0.00.
- **Lesson:** reconcile the way the books were built, then a tight tolerance is honest.

### 2. The independent review changed the design
The first version passed its tests. A separate reviewer (a fresh agent that saw only the story and
the diff) found:

| Severity | Finding | Outcome |
|---|---|---|
| High | Empty Silver input would write a false fraud list, or wipe Gold before failing | Fixed: input guards before any write |
| Medium | One missing FX rate or a day off by more than 1 cent would blame every journal, the genuine one included | Fixed: such days are reported once, unattributed |
| Medium | Two journals equal to the POS total: the one blamed depended on alphabetical order | Fixed: both reported as duplicate posting |
| Medium | Rows quarantined in Silver vanish before the reconciliation | Fixed: the job refuses to run while any are quarantined |
| Medium | A catch-all hid answer-key read errors | Fixed: only "file missing" skips scoring; an empty key fails |
| Medium | Revenue = account 4000 is itself a label | Accepted: one explicit setting; fake revenue on another account is out of this control's reach |
| Low | Three writes could leave tables from different runs | Fixed: compute and check first, then write |
| Low | Exception rows repeat day totals | Fixed: renamed `day_*` |
| Low | Weak tests (a disguised-journal test that could pass for the wrong reason) | Fixed: 9 sharper tests |
| Low | Reruns append score rows | Accepted: a timestamped history |

- **Lesson:** tests written by the author test what the author thought of. The reviewer's job is
  what the author did not think of.

## Acceptance criteria

- [x] GL revenue vs POS net sales in EUR, per store and day, and per month
- [x] Difference within EUR 0.01 on every clean store-day (21,218 of 21,218 at EUR 0.00)
- [x] Exceptions list exactly the 4 A3 journals: 4 found, 0 missed, 0 false positives
- [x] Each exception shows journal, store, date, amount and reason
- [x] Exceptions are findings; the job fails only on incomplete inputs
- [x] Tests in CI, including a disguised fake journal

## Review

> **TL;DR:** independent pass by a fresh agent on the story and diff; findings above.

- [x] Evidence: every criterion backed by a number (workspace run) or a named test
- [x] Break it: fake labelled POS, fake equal to the POS total, fake on a closed day, missing sales, off-by-EUR-5 journal
- [x] Security: no secrets, no new egress; Gold exposes journal descriptions to `finance-analysts` (acceptable); scores in `ops` (engineers only)
- [x] Cost: one single-node job run (m6gd.large, spot), cents per run
- [x] Data: every difference reported; nothing dropped; refuses partial inputs
- [x] Failure: compute-then-write; rerun overwrites Gold, appends one score row
- [x] Docs: story, cmdb, STATUS, LLD 3 updated
- [x] Simplicity: the FX join repeats Silver's on purpose (avoids cent drift)
