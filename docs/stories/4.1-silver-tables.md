## Context

> **TL;DR:** Bronze is the unopened delivery; Silver is unpacked and checked.

Bronze keeps every value as text, so nothing is lost at load time. Silver is where types,
keys and rules are enforced ([STATUS · Bronze, Silver, Gold](../../STATUS.md#bronze-silver-gold)).
Design choice at start: plain PySpark tasks in the existing bundle, not Lakeflow declarative
pipelines. Same deploy path as Bronze, already proven in the private VPC.

## How Spark cleans the data

> **TL;DR:** each source has a small spec; Spark applies it in one pass and splits good rows from bad.

Each source is described once, as data, in `jobs/silver.py`:

| Spec part | Example (`pos_sales`) |
|---|---|
| Column types | `business_date DATE`, `net_amount DECIMAL(18,2)`, `promo_flag BOOLEAN` |
| Business key | `(transaction_id, line_no)` |
| Rules (SQL) | `gross_amount = net_amount + vat_amount`, `quantity > 0` |
| References | `store_id` must exist in `silver.stores` |
| EUR conversion | `net_amount_eur` from `net_amount`, `currency`, `business_date` |

Then one generic function applies any spec:

| Step | Spark technique | What happens to a bad value |
|---|---|---|
| Type every column | `try_cast` returns null instead of failing | `"2026-13-45"` → null → reason `bad_type:business_date` |
| Required columns | Null or blank check | Empty `sku` → `missing:sku` |
| Rules | Each rule is a SQL expression | `rule:gross_equals_net_plus_vat` |
| References | Left join to the master's keys (broadcast when small) | Store `S999` → `ref:store_id` |
| EUR | Join to `silver.fx_daily` (broadcast) | No rate for that day → `no_fx_rate` |
| Collect reasons | `array_compact(array(when(...)))` | A list per row; empty = clean |
| Dedup | `row_number()` over the key, latest load first | Older copy dropped, counted |
| Split | Empty list → Silver; otherwise → `silver.quarantine` with the raw record as JSON | Nothing silently dropped |

Spark is **lazy**: these steps only build a plan. Work happens at the write, where the
optimiser fuses them into as few passes as possible. That laziness is also how the first
version went wrong (see tricky part 1).

**FX detail:** the ECB publishes on working days only. `silver.fx_daily` has one rate per
currency per day from the first sale to the last, carrying the last published rate over
weekends and holidays (a window with `last(..., ignorenulls)`), taking the first rate for
days before it was published (`first(..., ignorenulls)`), plus EUR at 1.

## How big the dataset is

> **TL;DR:** small on purpose: realistic shape, portfolio scale.

| Measure | Value |
|---|---|
| Files | ~482 MB of CSV (pos_sales 459 MB) |
| Rows | 4.2m total; pos_sales 3,940,360 |
| Period | 2025-01-01 → 2026-09-25, 40 stores, 1,200 products |
| Compute | One job cluster node (m6gd.xlarge: 4 vCPU, 16 GB) |

**Yes, it is deliberately small.** A real large retailer has thousands of stores and each
supermarket rings up a few thousand receipts a day; we generate about 60 per store per day.
That is roughly 1/1,000th of a real chain. We sized it to:

- fit the trial budget and a single small node;
- generate in ~2 minutes locally, so tests and demos stay fast;
- still be big enough that inefficient Spark code shows (it did).

The generator scales with two settings (`n_stores`, `base_txn_per_day`); the Silver code
does not change, you add workers. Tests use an even smaller config (6 stores, 27 days,
~9k sales lines) so the Spark tests run in ~90 seconds.

## Tricky parts

> **TL;DR:** a performance bug, an FX bug the quarantine caught, and three smaller surprises.

### 1. First run: 50+ minutes on one table, then timeout
- **Symptom:** the four master tables finished in minutes; `pos_sales` ran until the 60-min timeout.
- **Causes (my code):**
  1. each cached row carried typed columns, raw strings **and** a JSON copy of itself: ~3× memory on 8 GB, so it spilled to disk;
  2. the dedup sort ran three times (Silver count, duplicate count, write) because only the input was cached, not the ranked result;
  3. four full counts per source.
- **Fix:** slim cached rows (JSON built only for quarantined rows), one sort inside the write,
  counts read from the written Delta tables, broadcast joins for small tables, 4-vCPU node.
- **Lesson:** with lazy evaluation, every `count()` re-runs the whole plan. Count the table you wrote, not the DataFrame.

### 2. The quarantine caught my own bug
- **Symptom:** run 2 succeeded but quarantined 123 sales lines and 1 refund, on data that is clean by construction.
- **Diagnosis:** regenerated the files locally and re-checked every rule in pandas with exact decimals: 0 violations,
  so the bug was in Silver. All 123 lines were online-store sales on **2025-01-01**.
- **Cause:** `silver.fx_daily` started at the ECB's first published rate (2 January), so 1 January had no rate, not
  even EUR = 1. The refund returned one of those sales, so its reference failed too.
- **Fix:** the FX table spans from the earliest sale; days before the first rate take that first rate. New test.
- **Lesson:** this is why nothing is dropped silently. A filter would have lost 123 rows without anyone noticing.

### 3. The count check must not be circular
- Bronze = Silver + quarantined + duplicates can be true by construction. Written as
  bronze = clean + quarantined, it catches rows **multiplied** by a bad join (a duplicated FX
  rate would silently double sales) and rows lost in the split.

### 4. No Java on the workstation
- PySpark needs a JVM. Installed a user-level Temurin 17 JRE (no sudo) matching Databricks
  Runtime 17.3 (Spark 4.0). CI runners already have Java 17.

### 5. CSV habits
- Booleans arrive as `True`/`False` (pandas); `try_cast` handles them. Empty strings count as
  missing. The small test config has no prior year, so its budget is empty (handled in the test).

## Acceptance criteria

- [x] Dates, timestamps, decimals, integers, booleans typed
- [x] One row per business key; duplicates removed and counted
- [x] Rule breakers in `silver.quarantine` with source, key, reasons, raw record
- [x] Bronze rows accounted for, per source; the job fails otherwise
- [x] EUR column at the ECB rate of the day
- [x] Idempotent (full rebuild each run)
- [x] Tests in CI; runs under `finance-jobs` as the service principal
- [x] Full run on the workspace with counts recorded
