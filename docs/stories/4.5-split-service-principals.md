## Context

> **TL;DR:** it worked because one identity could do everything. That was the problem.

`terraform-platform` was created for Terraform ([2.3](2.3-workspace-as-code.md)); the data repo
reused it ([3.2](3.2-catalog-and-bundle-deploy.md)). A bug or compromise in data code therefore
ran with account-admin power.

## Identities

> **TL;DR:** each identity can do one job and was tested on what it must not do.

| Identity | Used by | Can | Proven it cannot |
|---|---|---|---|
| `terraform-platform` | Infra CI only | Account admin | (no longer used by the data repo) |
| `finance-data-deployer` | Data repo CI | Deploy the bundle, upload wheels to `ops.artifacts`, launch jobs as the runner | Change a grant ("no MANAGE on finance.silver"); create a cluster ("not authorized to create clusters") |
| `finance-pipeline-runner` | Jobs (`run_as`) | Read/write the five finance schemas, use the job cluster policy | Be a workspace admin; grant anything (GRANT refused, checked on every Gold run) |

## How it was done

> **TL;DR:** two phases, so no deploy ever ran on a missing grant.

1. **Infra PR #29:** both service principals, workspace access (the users group's entitlements
   are locked), the Service Principal User role (deployer → runner), schema grants. Apply: 11 added,
   2 changed, 0 destroyed.
2. **Credentials:** the deployer's secret created through the account API and piped straight into
   the data repo's GitHub secrets, never displayed.
3. **Jobs kept, not recreated:** ownership moved to the deployer and the three jobs bound to its
   bundle deployment, so their run history (evidence cited in earlier stories) survives.
4. **Data PR #18:** `run_as` → runner; Gold gate gains `runner_not_admin` and `runner_cannot_grant`.
5. **Infra PR #30 + data PR #19:** the access allow-list moves to a platform audit (below).

## Tricky parts

> **TL;DR:** one prediction held, one assumption was wrong, one mystery resolved itself.

### 1. Overwriting tables the runner does not own
- **Worry:** Silver and Gold overwrite tables owned by `terraform-platform`; an ownership transfer
  would have let the runner grant on its own tables.
- **Result:** plain MODIFY/CREATE_TABLE grants are enough. No ownership transfer, no side effect.

### 2. The runner cannot audit access (by design)
- **Symptom:** Gold refused to publish: "finance-analysts lacks USE SCHEMA/SELECT on gold".
- **Cause:** only owners and admins see other principals' grants; the runner saw only its own.
- **Fix:** `scripts/access_audit.py` in infra post-merge CI, as `terraform-platform`, over the
  catalog, schemas and every table and volume (which Terraform does not manage). First run:
  38 securables, 0 violations. The Gold job enforces the allow-list only when it can see others' grants.
- **Lesson:** separation of duties has a consequence: the identity that does the work cannot be
  the one that checks who may see it. Put each check with the identity entitled to run it.

### 3. A negative test that proved nothing
- The first "deployer cannot create a cluster" probe was refused for a missing security mode, not
  for lack of permission. Rerun with a valid request: "not authorized to create clusters".
- **Lesson:** a negative test must fail for the reason you are testing.

### 4. Lineage appeared (R-11)
- On the first run as the runner, `lineage_traced` passed: every Gold table traced to Bronze. The
  exact cause (uncached writes from PR #17 taking effect, the new identity, or delayed recording)
  was not isolated; recorded as such.
